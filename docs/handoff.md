## Foundation F1 — repository auto refresh

Core Feature Development: **FROZEN**. F1 adds no Git workflow. Next phase: **F2 / UI/UX Polish**.

The active Tauri repository session owns one `notify` watcher. `open_repository` stops the prior watcher, opens through `WorkingTree`, then watches the worktree recursively plus Git's resolved `--git-dir` and `--git-common-dir` (including external worktree metadata). The worktree parent is watched nonrecursively for disappearance. Watch setup failure leaves manual Refresh available and returns `watchWarning`. Each event is a hint; Rust classifies worktree, index, HEAD, refs/tags, and operation metadata. Unknown significant changes use conservative validation. Object/reflog/temp noise is ignored. A 250 ms quiet window and 1 s maximum burst coalesce events. The bounded channel overflows into conservative validation. Events arriving during validation remain queued for a later cycle.

Validation uses the existing `WorkingTree` mutex and system Git infrastructure: worktree/index/operation hints read structured status plus Git-owned operation/conflict state; HEAD hints also read branch and HEAD metadata; refs hints read branch/HEAD and branch list, with status refreshed only if HEAD changed. React receives a session-ID/sequence-tagged event with structured state, identity/refs, and history/diff/tag invalidations. External HEAD changes reset the first history/graph page; refs-only changes refresh decorations and branches; worktree/index changes update status and refresh or clear the selected diff; operation markers reconstruct the M10/M11 panel. Manual Refresh remains. No persisted Woo conflict truth or generic Git endpoint was added.

Woo's own mutations still perform their existing targeted refresh. The watcher never suppresses events based on a recent Woo command. React defers watcher events during an active mutation, then requests one fresh watcher validation instead of applying a possibly stale snapshot. Repository generation and frontend session ID prevent old-repository events from updating a new session. A failed validation sets a stable unavailable/error state once; parent watch events can trigger recovery. The watcher is event-driven, with no polling retry loop.

Tests: `watcher.rs` unit tests cover path classification, a native filesystem notification, bounded path/event coalescing, and 100 rapid hints in one validation cycle. Temporary-repository integration tests cover external edit, add, commit, checkout, branch/tag refs, conflicted merge entry/abort, stale session rejection, and metadata disappearance. Diagnostic process budget per validation: worktree/index = two Git processes (status and operation metadata); refs-only = three (identity and branch list); HEAD transition or conservative validation = up to five, plus one index-stage query when conflicts exist. The debounce adds approximately 250 ms after the last ordinary event, plus Git validation time; sustained bursts are capped at one second before validation. Three diagnostic shell runs against this OneDrive workspace **while Rust compilation was active** measured `git status` at 265–677 ms and operation-path `rev-parse` at 141–254 ms. That implies roughly 0.65–1.2 s from the last file event to a validated worktree result under this load, before IPC/rendering; it is not an idle-system benchmark. The event carries measured `validationMs` and coalesced count for later diagnostics. Native filesystem event latency and WebView frame timing remain platform-dependent and unmeasured.

Verification: frontend production build passed. The full Rust suite passed in an isolated temporary Cargo target directory: **35 unit tests and 70 integration tests**, including all F1 watcher tests and M1–M12 regressions. `cargo fmt --check`, Clippy with the three established pre-existing allowances (`manual_is_multiple_of`, `chunks_exact_to_as_chunks`, `useless_vec`), and `git diff --check` passed. `npm run tauri -- build --no-bundle` built the release executable; a hidden launch remained alive after four seconds. An initial full test run in the shared `src-tauri/target` directory hit an existing M8 child-process cancellation timeout while `tauri dev` was compiling, and a retry could not replace the live `woo.exe`; the isolated cancellation retry and complete isolated suite both passed. Native WebView click-through of an external edit was not available and was not claimed. Review found and fixed a stale event-after-mutation race, absent-vs-unborn HEAD serialization, missing metadata-directory removal classification, and an event-listener cleanup race. No known critical F1 architectural blocker remains.

Known limits: watcher APIs vary by filesystem (notably network shares and OneDrive); missed OS notifications remain possible, so manual Refresh is retained. A repository moved entirely out from under its watched parent requires reopening if no usable recovery event is delivered. External Git mutations are not serialized with Woo's mutex, so the Git read is authoritative at validation time but can change again immediately afterward; subsequent events converge it. M12 architecture: the M5 `DiffFile` carries a SHA-256 fingerprint of its bounded Git patch and a `partialStageable` flag. React selects a hunk or changed-line positions within one hunk; Rust owns patch generation and Git semantics. Under the existing repository mutex, `partial_stage` re-reads status, operation/conflict state, and the selected file's patch. A full-patch fingerprint rejects stale selections. Rust retains Git's file headers and builds one hunk patch; `git apply --cached --recount --whitespace=nowarn -` stages it, with `--reverse` for unstaging. Stdin carries the patch. Git's context check and atomic apply are the final authority. Working-tree files are never written by this operation. After an apply attempt, Rust returns status and both targeted file diffs, including after a nonzero Git result; React clears line selection and keeps history/graph/refs untouched.

Selection semantics: complete-hunk action uses the original Git hunk. For changed-line selection, stage converts unselected deletions to context and omits unselected additions; unstage omits unselected deletions and converts unselected additions to context. Replacement blocks pair old/new positions to keep unselected lines in place. Context is structural and cannot be selected. The diff fingerprint invalidates old hunk/line positions after any Git diff change. The UI offers partial controls only for ordinary modified tracked text. Untracked/new, deleted, renamed/copied, mode-changing, gitlink, binary, and conflicted files retain existing whole-file or conflict-resolution controls. No multiple-hunk transaction is offered.

Text handling: patch lines preserve Unicode, tabs, leading/trailing spaces, blank lines, and Git's no-newline marker. CRLF staging changes index content without rewriting the working file. Existing 2 MiB raw patch and 20,000-line limits remain. A selected diff that becomes stale is re-read and returned with a stable `stale_diff` error; `git apply` failure also returns refreshed state. If status itself cannot refresh, Woo requires a manual repository refresh rather than claiming old state is current. An external writer could race between Woo's re-read and Git's apply; Git context validation is relied upon and the mutation does not force application.

M10 implementation: `conflicts.rs` reconstructs merge state from Git's `MERGE_HEAD` path and message, and conflicted files from NUL-delimited `git ls-files -u -z` index stages. Stage 1 is base, 2 ours, and 3 theirs; absent stages remain absent. A merge remains active after the last conflict is staged until Git creates the merge commit. Conflict kinds are classified from the available stages; unusual rename/custom-driver cases may be reported as `other`, while the underlying stages remain available. The same conflict list can describe non-merge index conflicts, preparing the model for later operations. State is reconstructed on repository open or manual refresh, including merges started outside Woo.

Merge commands: Rust validates a selected local `refs/heads/` branch and runs `git merge --no-edit -- <ref>` under the existing session mutex. The result is classified from refreshed HEAD, branches, status, and merge markers: already up to date, fast-forward, clean merge, needs resolution, needs completion, or failure. A nonzero exit still triggers inspection; it never proves the repository is unchanged. Merge output is bounded to 1 MiB and has a 300-second timeout. Successful or failed merge refreshes HEAD/branches/status/operation state, clears stale diffs, and resets history/graph only when HEAD changed. Ordinary commit, checkout, stash create/apply/pop, and pull refuse an active merge. Other index conflicts also block starting a new merge.

Resolution: selecting a conflict loads only that file's base/ours/theirs Git index blobs and working copy. Each side has a 256 KiB text limit; binary, nonregular, or oversized content is represented without sending it as editor text. `Use Ours`/`Use Theirs` invokes Git checkout for an existing side followed by `git add`; a missing chosen side resolves as deletion with `git rm -f`. The user can edit ordinary text, save it with an optimistic working-copy comparison through a repository-confined temporary file, then stage with Git. Explicit resolve-as-deleted is available. Failed stage/resolve attempts refresh actual conflict and status state. There is no separate Woo resolved database. Manual refresh discovers external edits/staging.

Completion and abort: Woo loads Git's prepared `MERGE_MSG` for editing. `git commit --cleanup=verbatim -F -` receives Unicode/multiline text over stdin, preserving hooks, identity, and signing; comment lines visible in the editor are preserved literally. `git merge --abort` is a semantic command with two-click confirmation. Both operations inspect actual post-command state, including on failure. The frontend holds only selection/editor/request state; stale content requests are rejected by request identity, and existing repository generation/session guards protect history/diff. Merge/conflict mutations share the existing repository mutex.

It contains no duplicate commit metadata or pixel coordinates. Each `CommitHistoryPage` carries parallel `commits[]` and `graphRows[]`; array position is the link.

Layout: `src-tauri/src/graph.rs` processes newest-to-oldest topological history deterministically. An active lane owns exactly one expected future hash. A matching commit consumes that lane; an unrelated head uses the leftmost vacancy or appends. The first parent inherits the node lane unless it already has an active owner. Additional parents use existing owners or vacant lanes in parent order. Root commits terminate their lane. Trailing empty lanes are removed and internal vacancies reused. Every parent gets one ordered target lane, including octopus merges. The engine rejects malformed hashes, duplicate parents, duplicate commits within a page, duplicate lane ownership in a cursor, and more than 4,096 simultaneous lanes rather than drawing misleading output.

Pagination/lifecycle: the M4 opaque cursor now includes serialized active lane ownership after a page; the next request validates it and lays out only its new 100 commits. The predecessor check from M4 remains. Cursor input is capped at 300 KB. Repository open, commit, checkout, and history reload remount/reset `HistoryPanel`, discarding history and graph continuation together; existing generation/epoch checks reject stale responses. M4 deep skip-based Git pagination remains unchanged.

Renderer: `src/GraphRowView.tsx` draws semantic lanes as SVG in the same virtualized button and scroll surface as commit metadata. React never assigns lanes. Node/edge colors are deterministic by lane index; refs remain M4 labels. The gutter grows with loaded width through 12 visible lanes, then clips distant geometry and shows the hidden-lane count. Rendering paths are filtered to visible lanes; a 1,000-parent synthetic row produced only 12 visible paths. ADR 0002 records why row SVG was chosen over Canvas for M7.
